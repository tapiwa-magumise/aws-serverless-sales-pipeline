Serverless sales data pipeline

Walkthrough in five parts: what each piece does, why it was built that way, and how to talk about it in an interview.
Repo: github.com/gumagatsby/aws-serverless-sales-pipeline

The one-sentence pitch. Branches upload a sales CSV. Every row is checked within seconds, good rows become queryable with SQL, bad rows are kept with the reason they failed, every file gets an audit record, and someone is emailed if anything breaks. It's all Terraform, deployed by GitHub Actions with no stored AWS keys, and it costs nothing to run.

Part 1. The flow: what happens when a file is uploaded

  1. Upload. A branch puts weekly-sales-w41.csv into the raw S3 bucket under incoming/.
  2. Event. S3 sees a new .csv under incoming/ and sends an "object created" message to the SQS queue. Files elsewhere in the bucket, or not ending in .csv, are ignored.
  3. Trigger. Lambda polls the queue and runs the validator with up to 5 messages at a time. No more than 2 copies run at once.
  4. Claim. The validator writes an item to the DynamoDB audit table, but only if that file (name plus content fingerprint) has never been seen. If it has, the file is skipped. This is the duplicate guard.
  5. Validate. Each row is checked: date valid and not in the future, known branch, SKU shaped like ABC-123, units above zero, revenue and cost not negative, no duplicate rows.
  6. Write. Good rows go to curated/sales/dt=<today>/. Bad rows go to curated/rejected/dt=<today>/ with a list of every reason.
  7. Record. The audit item is updated with the status (LOADED, LOADED_WITH_REJECTS or FAILED), the counts and the finish time.
  8. Query. An analyst runs SQL in Athena. The Glue Data Catalog tells Athena what the files look like and where they live.
  9. If it breaks. A failed message goes back on the queue and is retried. After 3 failures it moves to the dead-letter queue. A CloudWatch alarm sees it and SNS emails you.

What you saw live: the sample file had 10 rows, 5 loaded and 5 rejected. Re-uploading it was skipped as a duplicate.

Part 2. The validator code

Two files, on purpose

FileJobWhy separate
rules.pyPure validation: takes text, returns loaded rows, rejected rows and reasons.No AWS code, so it's tested on a laptop in milliseconds (tests/test_rules.py). Business rules are easy to read, change and explain.
handler.pyPlumbing: reads from S3, writes to S3 and DynamoDB, handles retries.Keeps the AWS wiring in one place. If the storage changed, the rules wouldn't.

Key ideas in rules.py

  • Every reason, not just the first. _check_row collects all the problems in a row, so a branch fixes everything in one go.
  • Rows rejected, not files. One bad row doesn't block 499 good ones. The whole file fails only if a column is missing.
  • Decimal for money. Decimal("59.88") stays exact. Floats can turn it into 59.879999.

Key ideas in handler.py

# Idempotency: write only if this file_id has never been seen
audit.put_item(Item={...}, ConditionExpression="attribute_not_exists(file_id)")
  • file_id = key + ETag. The ETag is S3's fingerprint of the file contents. The same file uploaded twice has the same ID and is skipped. A corrected file has a new ETag and loads.
  • Releasing the claim. If processing crashes after the claim, the item is deleted so the retry can run. Without that, a crash would block the file forever.
  • batchItemFailures. Lambda tells SQS exactly which messages failed, so only those retry and the successful ones aren't processed twice.
  • Structured logs. Every log line is JSON ({"event": "file_processed", ...}), so it can be searched and turned into metrics.

How GitHub logs into AWS

  1. The job asks GitHub for a short-lived signed token (that's what id-token: write allows).
  2. The token says who's asking: repo:gumagatsby@266259364/aws-serverless-sales-pipeline@1422026046:ref:refs/heads/main.
  3. AWS checks the token against the OIDC provider and the role's trust policy, and issues credentials that last about an hour.
The problem you hit, and why the fix is better. The first deploy failed with Not authorized to perform sts:AssumeRoleWithWebIdentity. GitHub now includes the owner and repo ID numbers in the token, and the trust policy only expected the names. Matching on IDs means that if the repo were renamed and someone else registered the old name, they still couldn't use your AWS role.

Checkov exceptions

The newer Checkov in CI raised 21 findings. One was real (the curated bucket had no lifecycle rule) and was fixed. The rest need paid features (customer-managed KMS keys, cross-region replication, access logs, versioning) or were a false positive. Each is listed in .checkov.yml with its reason. Skipping a check with a written reason is a decision. Ignoring it silently is a risk.

Part 5. Design decisions and interview questions

Full reasoning is in docs/decisions.md. These are the questions an interviewer is most likely to ask, with answers in your own terms.

"Why put SQS between S3 and Lambda?"

With a direct trigger, a failure retries twice and is then lost unless you add a failure destination. With a queue, every file is a message: it retries, it ends up in a dead-letter queue I'm alerted about, and bursts are smoothed out. One extra component, free at this volume.

"What happens if the same file arrives twice?"

The audit write is conditional on the file ID (key plus ETag) not existing. The second attempt fails that condition and is skipped, so sales are never double-counted. I tested it live: the re-upload logged skipped_duplicate.

"Why JSON Lines and not Parquet?"

Parquet is better at scale, but writing it from Lambda needs pyarrow, about 100 MB and a layer. At weekly branch volumes gzip JSON is small and Athena reads it fine. I'd switch to Parquet, probably in a Glue job, at millions of rows a day.

"How do you keep it secure?"

No public buckets, encryption at rest, HTTPS only, a least-privilege Lambda role, no long-lived keys anywhere (OIDC pinned to the repo's IDs), and a Checkov scan on every change.

"How do you control cost?"

Serverless only, so nothing runs when idle. No KMS customer keys, NAT gateways or crawlers. Lifecycle expiry on raw files and query results. A 10 MB per-query cap in Athena. Budget alerts on the first cent.

"What would you change for a real client?"

Turn on what I skipped for cost: customer-managed KMS keys, point-in-time recovery, access logging, versioning, longer log retention. Scope the deploy role down from PowerUser, add a staging environment with a manual approval before production, and move the branch list into a reference table the business can maintain.

"How would someone support this?"

The runbook (docs/runbook.md) covers each alarm, how to find a failed file, how to replay the dead-letter queue (safely, because processing is idempotent), and how to answer "my file did nothing".

Try it yourself

# Upload the sample
aws s3 cp sample-data/weekly-sales-w41.csv s3://<raw bucket>/incoming/weekly-sales-w41.csv

# See the audit record
aws dynamodb scan --table-name ssp-load-audit --region eu-west-2

# Watch the Lambda logs live
aws logs tail /aws/lambda/ssp-validator --region eu-west-2 --follow

# Then in the Athena console: workgroup ssp-sales, Saved queries,
#   daily-margin-by-branch and rejection-reasons
